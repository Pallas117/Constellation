## Repo facts
- Node 26 LTS (`.nvmrc`), matching CI (Node 25 reached end of life on 2026-06-01; 26 is supported to 2029-04-30). Native modules (better-sqlite3) must be built with the same Node that runs them.
- Backend tests: `npm test` (node:test via tsx, writes bedrock data to a temp dir). Type check: `npm run quality:types` (strict tsc on the frontend, backend, e2e tests and scripts; keep it at 0 errors). Full gate: `npm run audit:adherence`.
- Frontend: `npm run dev` (8080), backend: `npm run dev:proxy` (3001), build: `npm run build`.
- Auth is better-auth on `.auth.db` (email/password + Google Workspace SSO when `GOOGLE_CLIENT_ID/SECRET` are set; SSO sign-ups limited to `SSO_ALLOWED_DOMAIN`; email/password sign-up is invite-only: only addresses in `SIGNUP_ALLOWED_EMAILS`, empty by default, so add your dev address to `.env`). `npm run auth:migrate`, then `npm run auth:set-role -- <email> <user|staff|operator|admin>`.
- Roles (each includes the ones below): user = live visualisation; staff = + Mesh onboarding of own devices; operator = + operator console and team status; admin = + manage roles and any device. New accounts are `user`.
- Public API routes are an explicit allowlist (`API_POLICY` in backend/rbac.ts: anything unlisted is 404, no session 401, wrong role 403). Never let the UI poll a route the role can't use: CyberTiger counts 401/403s and auto-blocks the IP.
- `tools/argo/` is a standalone Go module (`go test ./...`); see its README.
- Always-on local services: `scripts/ops/gauss-services.sh install|status|restart|uninstall` runs the backend (:3001) and built frontend (:8080) as LaunchAgents from a dedicated checkout (`Gauss Aurora.worktrees/live`), logs in `~/Library/Logs/gauss/`. To deploy new code there: merge it to main, `scripts/ops/gauss-services.sh gates record <clean checkout at the sha>` (runs the five gates under the gate lock and records them by tree), then `scripts/ops/gauss-services.sh deploy <sha> [fallback dir]` (it refuses to leave no fallback unless `--no-fallback`); it refuses commits not on origin/main or without a passing record unless `--emergency <reason>` (texted and recorded). Don't keep a session open to wait for gates: `scripts/ops/gauss-services.sh gates enqueue <clean worktree|sha>` hands the run to one detached runner (admitted by `claude-heavy`, one at a time, deduped by tree, skips trees that already passed, one `npm ci` while package-lock.json is unchanged, in its own checkout `<repo>.worktrees/gates`) and records it exactly like `gates record`; then archive the session. Add `--pr <N>` to put a PR on the merge train: the runner merges main into it just before the run (no force push; a conflict is texted) and merges the PR after a pass when the standing approval holds (CLEAN, contains main, not a draft, nothing under auth/crypto/TLS/secrets/CyberTiger/keys: those pass and wait for Josh); PRs stacked on it are retargeted to main. The runner runs a copy of the script that only moves forward: an enqueue replaces it only from a checkout whose HEAD contains the commit it came from, or with origin/main's script (else it prints "Runner kept: ..."; `gates result status` names that commit). Never edit its copy by hand. Later, any session: `gates result <sha>` (one line; exit 0 passed, 1 failed, 3 still queued), `gates result status` for the queue. Scripts that need a yes/no use `gates passed <sha>` (exit 0 only if that exact tree has a passing record). After each pass the runner runs `<gates dir>/hooks/after-pass <sha> [<pr>]` if present (the approved-merge job, merges only), before the next request can move main. Every local gate step has a time limit (about three times its usual time; `GAUSS_GATES_STEP_S` overrides): past it the step and its children are stopped, the result says `timeout`, and the queue goes on. The gatebox file is read again for every request. A stuck runner: `gates restart` stops it and its run without a result (requests stay queued), clears a gate lock whose owner is gone, and starts a fresh runner. Requests expire after 72 h; the awake guard restarts the runner after a reboot. `check` shows who deployed live and with which gates. It refreshes the fallback, switches live (keeping its data), and rolls back by itself if the services don't come up. Ops events (watchdog, failover, deploys, alerts, boots) are JSON lines in `~/Library/Logs/gauss/events.jsonl`: `scripts/ops/gauss-services.sh events --since 2h`.

## Working rules
- Branch from `origin/main` in your own worktree: `npm run wt:create -- <branch>`. For Linear issues use the issue's branch name (e.g. `jzwnathan/gau-6-…`) so the PR links to it; otherwise `<type>/<name>`. See `docs/WORKTREE_ARCHITECTURE.md`.
- Push early as a draft PR (nothing only on one machine); `git pull --ff-only` before committing in a shared folder; keep about 8 PRs open at most and merge stacks bottom-up.
- PR descriptions follow `.github/pull_request_template.md`, including the `### Developer Score` section CI validates.
- Never commit `.env*`, `.auth.db` or `data/mesh/`; never weaken TLS or put tokens in URLs.
